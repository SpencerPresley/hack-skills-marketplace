<objective>
End-to-end UAT for Phase 1: prove the plugin shell actually installs, coexists with v1 plugins, and emits its stub hook output at the expected session boundaries. This plan is the load-bearing acceptance gate for ROADMAP Phase 1 SC #4 and SC #5.

Purpose: Plan 01 and Plan 02 produce static files. They cannot tell you whether the install path actually works, whether `claude plugin details` actually sees both hooks, or whether SessionStart actually fires on `/clear`. Only running the install and observing the behavior closes those gaps. RESEARCH §"Pitfall 1" specifically calls out that SessionStart does NOT fire on install — it fires on the NEXT session boundary, which means the verification step needs a fresh session OR a `/clear` AFTER install. This plan is structured around that timing constraint.

Output: A `.planning/phases/01-plugin-mechanism-spike/01-03-SUMMARY.md` capturing the install command outputs, the `claude plugin details` listing, the coexistence proof with a v1 plugin, and direct quotes of the observed SessionStart + UserPromptSubmit stub marker text from Claude's context.

Why this plan is `autonomous: false`: the SessionStart and UserPromptSubmit hooks fire INSIDE Claude Code, which means the user (or a human running Claude Code) must observe Claude's behavior to confirm the stub text was injected. Pure CLI output from `claude plugin details` does not show whether hooks actually fired in a session — only that they are registered. Plan steps 1–3 are automated; step 4 is a `checkpoint:human-verify` that pauses for the user to run the install in their interactive Claude Code session and confirm the marker text appears.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local install path (CLI ↔ filesystem) | `claude plugin install` reads marketplace.json and copies the plugin tree from `./plugins/hack-skills-router/` to `~/.claude/plugins/cache/hack-skills-marketplace/hack-skills-router/`. This crosses from "working tree" to "user's local cache." |
| Hook execution surface | After install, hook scripts run in the user's shell on every session boundary and every prompt. Even stub scripts execute under the user's privileges. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | Plugin cache directory | mitigate | `claude plugin install` is the only mechanism that writes into the cache. Phase 1 does not author cache files directly. The cache state is reproducible — `uninstall` + `install` recreates it deterministically. Mitigation is "use the documented install command; don't write into the cache by hand." |
| T-03-02 | Spoofing | Marketplace identity | accept | The marketplace is registered as a LOCAL path during Phase 1 (Task 2 re-registers). After uninstall + Phase 4 push, the GitHub form takes over. During Phase 1 spike, the user's own working tree is the source — no spoofing surface. |
| T-03-03 | Elevation of Privilege | Hook execution after install | accept | Hooks run with user shell privileges. Phase 1 scripts are stubs — no privileged calls. This is the standard CC plugin trust model (per RESEARCH §"Security Domain" — explicitly out of scope for the mechanism spike). Phase 3's planner will need to address dynamic content trust when the stubs are replaced. |
| T-03-04 | Repudiation | UAT observability | mitigate | The human-verify step explicitly requires the user to quote the observed marker text into the SUMMARY. If the user reports "approved" without evidence, the SUMMARY would be empty, which is a failure mode the next phase's reviewer (or the checker agent) catches. Plan also gives an explicit `claude --debug` fallback for the case where the marker text isn't visible in normal session output. |
